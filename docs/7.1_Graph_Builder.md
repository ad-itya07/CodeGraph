# 7.1 Graph Builder

## What Does This Do?

> **Transforms a `ParsedRepository` into a fully indexed, validated `Graph` ready for analysis.**

The `GraphBuilder` is a pure construction class — it takes the flat, raw output of the Parser (files, symbols, relationships, package metadata) and assembles it into the five-map `Graph` structure. After `build()` returns, the graph is immutable from the builder's perspective: all subsequent work is reads only.

## Class Signature

```ts
class GraphBuilder {
    build(repository: ParsedRepository): Graph
}
```

`GraphBuilder` has no constructor parameters and no persistent state. Every call to `build()` creates and returns a completely independent `Graph` from scratch.

---

## Build Phases

`build()` executes in **five sequential phases**:

```ts
build(repository: ParsedRepository): Graph {
    const graph: Graph = { /* empty maps */ };

    // Phase 1: Nodes
    this.addFileNodes(graph, repository);
    this.addSymbolNodes(graph, repository);
    this.addDependencyNodes(graph, repository);
    this.addModuleNodes(graph, repository);

    // Phase 2: Edges
    this.addRelationshipEdges(graph, repository.relationships);

    // Phase 3 & 4: Validation
    this.validateGraph(graph);
    this.validateIndexes(graph);

    return graph;
}
```

Nodes are always added before edges. This ordering is required because `validateGraph` verifies that every edge references existing nodes — if edges were added first, validation would always fail.

---

## Phase 1: Node Construction

### `addFileNodes`

Iterates `repository.files` and creates one `FileNode` per source file.

```ts
const node: FileNode = {
    id:       getGraphNodeId("file", file.filePath),
    kind:     "file",
    filePath: file.filePath,
};
```

The `id` is `"file:/absolute/path/to/file.ts"`. The file path doubles as both the lookup key and the payload — there is no extra metadata stored on a file node.

### `addSymbolNodes`

Iterates all symbols across all files and creates one `SymbolNode` per symbol. The file association is baked in at node creation time:

```ts
const node: SymbolNode = {
    id:         getGraphNodeId("symbol", symbol.id),
    kind:       "symbol",
    name:       symbol.name,
    symbolKind: symbol.symbolKind,
    fileId:     getGraphNodeId("file", file.filePath),  // ← back-reference to owning file
};
```

`fileId` is a pre-computed graph node ID pointing to the file that owns this symbol. This lets any downstream code look up a symbol's file in O(1) without traversing edges.

### `addDependencyNodes`

Constructs `DependencyNode` entries from `repository.metadata.packageJsons` — **not** from relationships. This is a deliberate design decision:

> Dependency nodes are sourced from `package.json` metadata, not inferred from import edges.

Why? Because `package.json` is the authoritative source of what packages the project declares as dependencies. Import edges tell you which packages are *used*, but they don't tell you which version is declared or whether the package is a dev dependency. The node carries version and package.json path information that would be lost if constructed from relationships alone.

```ts
const node: DependencyNode = {
    id:              getGraphNodeId("dependency", dependency.id),
    kind:            "dependency",
    name:            dependency.name,
    version:         dependency.version,
    packageJsonPath: packageJson.filePath,
};
```

Both `dependencies` and `devDependencies` from each `package.json` are included.

### `addModuleNodes`

Constructs `ModuleNode` entries by scanning `repository.relationships` for any relationship where `targetKind === "module"`:

```ts
if (relationship.targetKind !== "module") continue;

const node: ModuleNode = {
    id:   getGraphNodeId("module", relationship.targetId),
    kind: "module",
    name: relationship.targetId,
};
```

A module is any import target that the parser couldn't resolve to a known file or a declared npm package — Node.js built-ins (`"fs"`, `"path"`), unrecognized packages, etc. Because module nodes are generated from the relationship list itself, they only appear in the graph if something actually imports them.

### Deduplication in `addNode`

All four node-creation methods funnel through the same private `addNode` helper:

```ts
private addNode(graph: Graph, node: GraphNode): void {
    if (graph.nodes.has(node.id)) return;  // ← deduplication guard

    graph.nodes.set(node.id, node);

    if (!graph.nodesByKind.has(node.kind)) {
        graph.nodesByKind.set(node.kind, new Set());
    }
    graph.nodesByKind.get(node.kind)!.add(node.id);
}
```

The `if (graph.nodes.has(node.id)) return` guard silently skips duplicates instead of throwing. This matters for:
- **Module nodes**: the same module (e.g., `"fs"`) may appear in multiple import relationships across many files, but should only have one node in the graph.
- **Dependency nodes**: the same package may appear in multiple `package.json` files in a monorepo.

## Phase 2: Edge Construction

### `addRelationshipEdges`

Converts every `ParsedRelationship` into a `GraphEdge`. The key transformation is **ID normalization**: the parser stores raw IDs (file paths, symbol IDs, package names), while the graph uses prefixed IDs.

```ts
const edge: GraphEdge = {
    id:               relationship.id,
    sourceId:         getGraphNodeId(relationship.sourceKind, relationship.sourceId),
    targetId:         getGraphNodeId(relationship.targetKind, relationship.targetId),
    relationshipKind: relationship.relationshipKind,
};
```

So a relationship `{ sourceId: "/path/auth.ts", sourceKind: "file", targetId: "express", targetKind: "dependency", kind: "imports" }` becomes an edge `{ sourceId: "file:/path/auth.ts", targetId: "dependency:express", ... }`.

### Deduplication and Index Update in `addEdge`

```ts
private addEdge(graph: Graph, edge: GraphEdge): void {
    if (graph.edges.has(edge.id)) return;  // ← deduplication guard

    graph.edges.set(edge.id, edge);

    // Update outgoing index
    if (!graph.outgoingEdges.has(edge.sourceId)) {
        graph.outgoingEdges.set(edge.sourceId, new Set());
    }
    graph.outgoingEdges.get(edge.sourceId)!.add(edge.id);

    // Update incoming index
    if (!graph.incomingEdges.has(edge.targetId)) {
        graph.incomingEdges.set(edge.targetId, new Set());
    }
    graph.incomingEdges.get(edge.targetId)!.add(edge.id);
}
```

Every edge addition updates **both** directional indexes atomically. This ensures `outgoingEdges` and `incomingEdges` are always consistent with the primary `edges` map.

---

## Phase 3: Graph Validation

### `validateGraph` — Referential Integrity

Checks that every edge references existing nodes:

```ts
private validateGraph(graph: Graph): void {
    for (const edge of graph.edges.values()) {
        if (!graph.nodes.has(edge.sourceId)) {
            throw new GraphValidationError(edge.id, edge.sourceId, edge.targetId);
        }
        if (!graph.nodes.has(edge.targetId)) {
            throw new GraphValidationError(edge.id, edge.sourceId, edge.targetId);
        }
    }
}
```

If a `ParsedRelationship` references an entity that wasn't turned into a node (e.g., a symbol that failed to parse, or a file that wasn't walked), this validation will catch it and throw a `GraphValidationError`.

This is the graph equivalent of a foreign key constraint — no edge can dangle to a non-existent node.

### `validateIndexes` — Index Consistency

Checks that the secondary indexes match the primary stores:

```ts
private validateIndexes(graph: Graph): void {
    // Every node must appear in nodesByKind
    for (const node of graph.nodes.values()) {
        const nodeIds = graph.nodesByKind.get(node.kind);
        if (!nodeIds?.has(node.id)) {
            throw new GraphIndexError(`Node "${node.id}" is missing from nodesByKind index`);
        }
    }

    // Every edge must appear in both directional indexes
    for (const edge of graph.edges.values()) {
        const outgoing = graph.outgoingEdges.get(edge.sourceId);
        if (!outgoing?.has(edge.id)) {
            throw new GraphIndexError(`Edge "${edge.id}" is missing from outgoingEdges index`);
        }

        const incoming = graph.incomingEdges.get(edge.targetId);
        if (!incoming?.has(edge.id)) {
            throw new GraphIndexError(`Edge "${edge.id}" is missing from incomingEdges index`);
        }
    }
}
```

In normal operation, this validation should never fail — `addNode` and `addEdge` maintain consistency as they run. The validation is a safety net for catching bugs in the builder's own mutation logic during development.

## Node ID Format Reference

| Node Kind | Raw Input | Resulting Graph Node ID |
|-----------|-----------|------------------------|
| `file` | `/repo/src/auth.ts` | `file:/repo/src/auth.ts` |
| `symbol` | `/repo/src/auth.ts:12:4:validateToken` | `symbol:/repo/src/auth.ts:12:4:validateToken` |
| `dependency` | `express` (name from package.json) | `dependency:express` |
| `module` | `fs` (Node built-in) | `module:fs` |

The `getGraphNodeId` utility applies the prefix:

```ts
export function getGraphNodeId(kind: GraphNodeKind, id: string): string {
    return `${kind}:${id}`;
}
```

---

## What GraphBuilder Does NOT Do

- It does not modify the `ParsedRepository` it receives.
- It does not store the built graph — the caller is responsible for holding the reference.
- It does not perform any graph traversal or analysis — that is the analytics engine's job.
- It does not know about `GraphQuery` — the two classes are independent.

---

## Design Decisions

**Nodes before edges**: The build order guarantees that `validateGraph` can check referential integrity immediately after edge construction. If the order were reversed, every edge would reference not-yet-created nodes.

**`addNode` silently deduplicates**: Throwing on duplicate nodes would require all callers to pre-check existence. Silent deduplication is safer — it matches the "idempotent build" semantics where re-processing the same input always yields the same graph.

**Module nodes are derived from relationships**: Module nodes don't come from a dedicated metadata extractor (unlike dependency nodes). Instead, the builder scans `repository.relationships` for `targetKind === "module"` entries. This keeps the graph fully self-consistent: a module node only exists if something actually imports it, so there are no dangling "known but unused" module nodes in the graph.

**Two validation phases**: Separating graph validation (referential integrity) from index validation (internal consistency) makes debugging faster — if the graph validation passes but index validation fails, the bug is in `addNode`/`addEdge`, not in the source data.
