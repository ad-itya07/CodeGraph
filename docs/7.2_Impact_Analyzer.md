# 7.2 Impact Analyzer

## What Question Does This Answer?

> **"If I change symbol X, which other parts of the codebase will be affected?"**

Equivalently: *"Who depends on X?"* or *"Which nodes are upstream consumers of X?"*

This is the reverse of asking what X itself uses. Instead of following X's own dependencies forward, the Impact Analyzer walks **backward** through the graph — against the direction of the edges — to find every node that has a direct or transitive structural relationship with X as its target.

### Concrete Example

Suppose you have this call graph in your codebase:

```
AuthService.login → TokenService.generate → CryptoUtil.sign
                                           → CryptoUtil.hash
UserController.register → AuthService.login
AdminController.login   → AuthService.login
```

If you are about to change the signature of `CryptoUtil.sign`, the Impact Analyzer will tell you:

```
impactedNodeIds = [
    "TokenService.generate",   // depth 1 — calls sign directly
    "AuthService.login",       // depth 2 — calls TokenService.generate
    "UserController.register", // depth 3 — calls AuthService.login
    "AdminController.login",   // depth 3 — calls AuthService.login
]
```

You now know that four other functions will potentially need review or testing.

## Class Signature

```ts
class ImpactAnalyzer {
    constructor(private readonly traversal: GraphTraversal) {}

    analyze(sourceNodeId: string, options: ImpactAnalysisOptions): ImpactAnalysisResult
}
```

### Input

```ts
// Parameter
sourceNodeId: string   // The node ID of the symbol or file being changed

// Options
interface ImpactAnalysisOptions {
    maxDepth?: number;
}
```

| Parameter | Type | Required | Meaning |
|-----------|------|----------|---------|
| `sourceNodeId` | `string` | ✅ | The node whose impact you are analyzing. This is the node you plan to change. |
| `maxDepth` | `number` | ❌ | Maximum number of hops to traverse backward. Omitting it gives the full transitive impact. Setting it to `1` gives only direct callers/importers. |

### Output

```ts
interface ImpactAnalysisResult {
    sourceNodeId: string;
    impactedNodeIds: string[];
    depthByNode: Map<string, number>;
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `sourceNodeId` | `string` | Echoed back for traceability. |
| `impactedNodeIds` | `string[]` | IDs of all nodes that would be affected by a change to `sourceNodeId`. Ordered by BFS discovery (nearest first). |
| `depthByNode` | `Map<string, number>` | For each impacted node, how many hops back it is. Depth 1 = direct consumers; depth 2 = consumers of consumers; etc. |

## Algorithm

The `ImpactAnalyzer` is a thin wrapper over `GraphTraversal`. It does not implement its own traversal — it configures the traversal with the correct parameters for impact analysis and returns the result.

```ts
analyze(sourceNodeId: string, options: ImpactAnalysisOptions = {}): ImpactAnalysisResult {
    const traversalResult = this.traversal.traverse(sourceNodeId, {
        direction: "incoming",       // ← Walk backward (against edge direction)
        relationshipKinds: [
            "calls",
            "imports",
            "extends",
            "implements",
            "instantiates",
        ],
        maxDepth: options.maxDepth,
    });

    return {
        sourceNodeId,
        impactedNodeIds: traversalResult.nodes,
        depthByNode: traversalResult.depthByNode,
    };
}
```

### Why `direction: "incoming"`?

In the CodeGraph edge model, an edge `A → B` with kind `"calls"` means **A calls B**. The arrow points from the caller to the callee. So if you change `B`, the node that is affected is `A`, not anything downstream of `B`.

To find who is affected by `B`, you need to find all nodes that have `B` as their edge target — i.e., you traverse edges in the **incoming** direction. The traversal engine handles this by looking up `graph.incomingEdges.get(currentNodeId)` and then following `edge.sourceId` instead of `edge.targetId`.

### Why These Specific `relationshipKinds`?

| Kind | Why it's included |
|------|-----------------|
| `calls` | Function/method calls — changing a function's behavior/signature affects every caller. |
| `imports` | File-level imports — changing an export affects every file that imports it. |
| `extends` | Inheritance — changing a base class affects every subclass. |
| `implements` | Interface implementation — changing an interface affects every class that implements it. |
| `instantiates` | `new` expressions — changing a constructor signature affects every call site that instantiates the class. |

`"exports"` and `"references"` are intentionally excluded. `"exports"` is a metadata edge (file exports a symbol) and doesn't represent a runtime dependency. `"references"` is a type-level reference that may not constitute a behavioral dependency.

---

## What It Does NOT Do

- It does not tell you *how* the callers are affected — only that they are.
- It does not filter by node kind. Both file nodes and symbol nodes can appear in `impactedNodeIds`.
- It does not detect whether the impact is breaking or non-breaking. That is a semantic question beyond graph structure.

---

## Design Notes

**Delegation to `GraphTraversal`**: The `ImpactAnalyzer` takes a `GraphTraversal` instance, not a `Graph` directly. This is a deliberate layering decision — the BFS logic lives in exactly one place, and analyzers that need multi-hop reachability (impact, dependency) compose with the traversal primitive rather than each reimplementing BFS. Analyzers that need finer algorithmic control (cycle detection, topological sort) take the `Graph` directly.

**Relationship with `DependencyAnalyzer`**: `ImpactAnalyzer` and `DependencyAnalyzer` are exact inverses of each other — same relationship kinds, opposite direction. Impact = "who uses me". Dependency = "what do I use".
