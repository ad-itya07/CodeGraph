# 7.6 Connectivity Analyzer

## What Question Does This Answer?

> **"How many things depend on X (fan-in), and how many things does X depend on directly (fan-out)?"**

The `FanInOutAnalyzer` measures the **degree** of a node in the code graph — specifically the count of its incoming and outgoing edges. These two numbers are among the most fundamental connectivity metrics in software architecture analysis.

- **Fan-in**: The number of other entities that directly consume, call, or depend on X. High fan-in = X is widely used.
- **Fan-out**: The number of entities that X directly consumes, calls, or depends on. High fan-out = X has many direct dependencies.

### Concrete Examples

```
TokenService.generate is called by:
  - AuthService.login
  - SessionService.refresh
  - OAuthService.exchange

  fan-in  = 3  (three callers)

TokenService.generate calls:
  - CryptoUtil.sign
  - JwtEncoder.encode

  fan-out = 2  (two direct dependencies)
```

A utility like `CryptoUtil.hash` might have:
- `fan-in = 15`  (used by many things)
- `fan-out = 0`  (depends on nothing in the codebase)

An entry-point like `main.ts` might have:
- `fan-in = 0`   (nothing imports it)
- `fan-out = 20` (bootstraps many modules)

## Class Signature

```ts
class FanInOutAnalyzer {
    constructor(private readonly graph: Graph) {}

    analyze(nodeId: string): FanInOutResult
}
```

### Input

```ts
nodeId: string   // The node whose fan-in and fan-out you want to measure
```

| Parameter | Type | Required | Meaning |
|-----------|------|----------|---------|
| `nodeId` | `string` | ✅ | The node to measure. Can be a file node or a symbol node. |

### Output

```ts
interface FanInOutResult {
    nodeId: string;
    fanIn: number;
    fanOut: number;
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `nodeId` | `string` | Echoed back. |
| `fanIn` | `number` | Total count of **incoming** edges to this node (regardless of edge type). |
| `fanOut` | `number` | Total count of **outgoing** edges from this node (regardless of edge type). |

---

## Algorithm

The implementation is O(1) per call because the `Graph` pre-indexes both edge sets at construction time:

```ts
analyze(nodeId: string): FanInOutResult {
    const incomingEdges = this.graph.incomingEdges.get(nodeId) ?? new Set();
    const outgoingEdges = this.graph.outgoingEdges.get(nodeId) ?? new Set();

    return {
        nodeId,
        fanIn:  incomingEdges.size,
        fanOut: outgoingEdges.size,
    };
}
```

`graph.incomingEdges` and `graph.outgoingEdges` are both `Map<string, Set<string>>` built by `GraphBuilder` at parse time. Each lookup is a single map access, and `.size` on a `Set` is a built-in O(1) property — no edge iteration is needed.

---

## What "All Edge Types" Means

Unlike the traversal-based analyzers (Impact, Dependency) which filter to structural relationship kinds, `FanInOutAnalyzer` counts **all edges** regardless of `relationshipKind`. This means:

| Edge kind | Counted? |
|-----------|---------|
| `calls` | ✅ |
| `imports` | ✅ |
| `extends` | ✅ |
| `implements` | ✅ |
| `instantiates` | ✅ |
| `exports` | ✅ |
| `references` | ✅ |

This is intentional. Fan-in/fan-out is a raw connectivity metric that describes the node's structural position in the overall graph. Filtering by edge type would give a narrower but less representative picture of the node's total coupling. If the caller wants fan-in/fan-out restricted to a specific edge kind, they would need to filter the edge sets manually.

## Interpretation Guide

The fan-in and fan-out values, taken together, are a powerful diagnostic tool:

| Pattern | fan-in | fan-out | Interpretation |
|---------|--------|---------|----------------|
| **Utility / Leaf** | High | Low | Widely consumed, low coupling. Ideal. |
| **Entry point** | Low | High | Bootstraps many things. Normal for top-level files. |
| **Hub / God node** | High | High | Bottleneck. Both many consumers and many dependencies. Fragile, risky to change. |
| **Isolated node** | 0 | 0 | Not connected to anything. Likely dead code. |
| **Pure consumer** | 0 | High | Consumes many things but nobody uses it. Potentially dead code. |
| **Pure dependency** | High | 0 | A foundational leaf (e.g., a constants file or a pure utility). Very stable. |

The **instability metric** from Robert C. Martin's Package Principles is derived from these two values:

```
Instability(X) = fan-out / (fan-in + fan-out)
```

- Instability = 0 → fully stable (nothing it depends on can change)
- Instability = 1 → fully unstable (nothing depends on it, it can change freely)

The `FanInOutResult` provides the raw inputs (`fanIn`, `fanOut`) for computing this metric.

## Design Notes

**Why not filter by edge kind?** Because fan-in and fan-out are intentionally broad measures of node degree. The Dependency and Impact analyzers already provide filtered, multi-hop reachability. The Connectivity Analyzer's role is to give a fast, unfiltered snapshot of how connected a node is.

**Why not return the actual edge IDs?** The `FanInOutResult` only returns counts, not the edge ID sets. If the caller needs the actual edges, they can directly access `graph.incomingEdges.get(nodeId)` and `graph.outgoingEdges.get(nodeId)`. The analyzer keeps its result minimal because counts are the actionable data for all connectivity-based use cases (sorting, ranking, dashboard display).

**Applicability to any node kind**: The analyzer is node-kind-agnostic. You can query fan-in/fan-out for a file node (to measure module coupling) or a symbol node (to measure function/class coupling) using the same method.
