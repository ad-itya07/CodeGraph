# 9.1 Cycle Health

## What Question Does This Answer?

> **"What fraction of this repository's files and symbols are caught inside circular dependency structures?"**

More specifically: *"Do any groups of nodes in the graph form strongly connected components — meaning they are mutually reachable through a particular relationship type — and if so, how many nodes are affected relative to the total?"*

Cycle Health is the single most heavily weighted metric in the Health Index (28%). Circular relationships are architecturally significant because they:

1. Prevent topological ordering — you cannot reason about which module initializes before another.
2. Increase the blast radius of change — changing any node in a cycle can affect all other nodes in that cycle.
3. Complicate testing — cycles often make it impossible to test a unit in isolation without mocking the rest of the cycle.
4. Can cause build failures — some module systems (like ES Modules in strict mode) reject import cycles entirely.

## TypeScript Interface

```ts
export interface CycleHealthResult {
    score: number;

    cycleCount: number;

    cyclicFileCount: number;
    cyclicSymbolCount: number;

    fileCycleRatio: number;
    symbolCycleRatio: number;
}
```

| Field | Type | Description |
|-------|------|-------------|
| `score` | `number` | Normalized health score, 0–100. Higher is healthier. |
| `cycleCount` | `number` | Total number of distinct strongly connected components identified as cyclic. |
| `cyclicFileCount` | `number` | Number of distinct file nodes that participate in at least one file-import cycle. |
| `cyclicSymbolCount` | `number` | Number of distinct symbol nodes that participate in at least one symbol-level cycle. |
| `fileCycleRatio` | `number` | Fraction of total file nodes that are in a cycle: `cyclicFileCount / totalFiles`. |
| `symbolCycleRatio` | `number` | Fraction of total symbol nodes that are in a cycle: `cyclicSymbolCount / totalSymbols`. |

---

## What "Cycle" Means in CodeGraph

CodeGraph does not use the word "cycle" loosely. A cycle is formally defined as a **Strongly Connected Component (SCC)** containing more than one node, or a single node with a self-loop edge.

A Strongly Connected Component is a maximal group of nodes such that every node in the group can reach every other node in the group by following directed edges.

### Concrete Example: File Import Cycle

```
auth.ts   ──imports──►  user.ts
user.ts   ──imports──►  profile.ts
profile.ts ──imports──►  auth.ts   ← closes the cycle
```

`{auth.ts, user.ts, profile.ts}` form a single SCC. All three files are counted as cyclic. The `cycleCount` increases by 1 (one SCC found). The `cyclicFileCount` increases by 3.

### Concrete Example: Symbol Call Cycle

```
isEven(n) ──calls──► isOdd(n-1)
isOdd(n)  ──calls──► isEven(n-1)
```

These two symbols form a symbol-call cycle. Both are added to `cyclicSymbolIds`. `cycleCount` increases by 1. `cyclicSymbolCount` increases by 2.

### Concrete Example: Self-loop

```
factorial ──calls──► factorial
```

A single-node SCC is only considered cyclic when it contains a self-loop. `cycleCount` increases by 1. `cyclicSymbolCount` increases by 1.

## Cycle Types Analyzed

CodeGraph analyzes five relationship types for cycles:

| Cycle Type | Node Kind | Relationship Kind | What It Detects |
|------------|-----------|-------------------|-----------------|
| `file-import` | `file` | `imports` | Circular module imports |
| `symbol-call` | `symbol` | `calls` | Mutual/direct function recursion |
| `symbol-inheritance` | `symbol` | `extends` | Circular class inheritance |
| `symbol-implementation` | `symbol` | `implements` | Circular interface implementation |
| `symbol-instantiation` | `symbol` | `instantiates` | Circular constructor/factory dependencies |

Each type is run as an independent graph projection. An import cycle among files is completely separate from a call cycle among symbols.

File-import cycles are counted in `cyclicFileCount`. All other cycle types contribute to `cyclicSymbolCount`.

---

## Algorithm

Cycle detection is delegated to `CycleAnalyzer`, which runs **Tarjan's Strongly Connected Components algorithm** over each relationship projection.

Tarjan's SCC runs in O(V + E) where V is the number of nodes of the relevant kind and E is the number of edges of the relevant relationship kind. This is optimal — finding all cycles without examining all edges is impossible.

See [9.4 Cycle Analyzer](./8.4_Cycle_Analyzer.md) for the full algorithmic documentation.

## Raw Measurements

### Step 1: Collect cyclic node sets

```ts
const cyclicFileIds   = new Set<string>();
const cyclicSymbolIds = new Set<string>();

for (const cycle of cycles) {
    if (cycle.type === "file-import") {
        for (const nodeId of cycle.nodeIds) {
            cyclicFileIds.add(nodeId);
        }
        continue;
    }

    for (const nodeId of cycle.nodeIds) {
        cyclicSymbolIds.add(nodeId);
    }
}
```

Node IDs are stored in Sets to ensure that a node appearing in multiple overlapping cycles is only counted once.

### Step 2: Compute cycle ratios

$$
\text{FileCycleRatio} = \frac{|\text{cyclicFileIds}|}{|\text{totalFiles}|}
$$

$$
\text{SymbolCycleRatio} = \frac{|\text{cyclicSymbolIds}|}{|\text{totalSymbols}|}
$$

If `totalFiles = 0`, the file ratio is treated as `0`. If `totalSymbols = 0`, the symbol ratio is treated as `0`. This prevents division-by-zero for repositories that contain only one kind of node.

### Step 3: Combine into a single cycle ratio

$$
\text{CycleRatio} = \frac{\text{FileCycleRatio} + \text{SymbolCycleRatio}}{2}
$$

This gives equal weight to file-level and symbol-level cyclicity. A repository that is entirely cycle-free at the file level but has 20% of its symbols in call cycles will report a cycle ratio of 0.10.

---

## Normalization

### Calibration reference

The cycle metric uses a bounded normalization approach with a calibration reference point:

$$
R_{\text{cycle}} = 0.10
$$

This value means: *"a repository where 10% (or more) of the relevant nodes are cyclic is considered to have reached the maximum modeled cycle risk."*

This is not a universal software-engineering standard. It is a CodeGraph calibration parameter.

### Normalized risk

$$
\text{NormalizedRisk} = \min\left(\frac{\text{CycleRatio}}{0.10},\ 1\right)
$$

The `min(..., 1)` cap ensures the normalized risk never exceeds 1.0, which would otherwise produce a negative health score.

### Health score

$$
\text{CycleHealth} = 100 \times (1 - \text{NormalizedRisk})
$$

This is **linear normalization**. The score decreases linearly from 100 (zero cyclic nodes) to 0 (10% or more of nodes are cyclic).

### Score behavior table

| CycleRatio | NormalizedRisk | CycleHealth |
|-----------|---------------|------------|
| 0.00 (0%) | 0.00 | 100.0 |
| 0.01 (1%) | 0.10 | 90.0 |
| 0.02 (2%) | 0.20 | 80.0 |
| 0.05 (5%) | 0.50 | 50.0 |
| 0.08 (8%) | 0.80 | 20.0 |
| 0.10 (10%)| 1.00 | 0.0 |
| 0.20 (20%)| 1.00 (capped) | 0.0 |

Once the cycle ratio exceeds 10%, the score is capped at 0. The metric models no additional health degradation beyond this calibration point.

## Full Implementation

```ts
export function calculateCycleHealth(graph: Graph): CycleHealthResult {
    const cycleAnalyzer = new CycleAnalyzer(graph);
    const cycles = cycleAnalyzer.analyze().cycles;

    const cyclicFileIds   = new Set<string>();
    const cyclicSymbolIds = new Set<string>();

    for (const cycle of cycles) {
        if (cycle.type === "file-import") {
            for (const nodeId of cycle.nodeIds) cyclicFileIds.add(nodeId);
            continue;
        }
        for (const nodeId of cycle.nodeIds) cyclicSymbolIds.add(nodeId);
    }

    const totalFiles   = graph.nodesByKind.get("file")?.size   ?? 0;
    const totalSymbols = graph.nodesByKind.get("symbol")?.size ?? 0;

    const fileCycleRatio   = totalFiles   === 0 ? 0 : cyclicFileIds.size   / totalFiles;
    const symbolCycleRatio = totalSymbols === 0 ? 0 : cyclicSymbolIds.size / totalSymbols;

    const cycleRatio = (fileCycleRatio + symbolCycleRatio) / 2;

    const normalizedRisk = Math.min(cycleRatio / 0.10, 1);
    const score          = 100 * (1 - normalizedRisk);

    return {
        score,
        cycleCount:        cycles.length,
        cyclicFileCount:   cyclicFileIds.size,
        cyclicSymbolCount: cyclicSymbolIds.size,
        fileCycleRatio,
        symbolCycleRatio,
    };
}
```

## Worked Examples

### Example A — Near-perfect repository

```text
Total files:   1170
Cyclic files:  0
Total symbols: 1310
Cyclic symbols: 1

FileCycleRatio   = 0 / 1170   = 0.000000
SymbolCycleRatio = 1 / 1310   = 0.000763

CycleRatio    = (0.000000 + 0.000763) / 2 = 0.000382
NormalizedRisk = min(0.000382 / 0.10, 1) = 0.00382
CycleHealth    = 100 × (1 − 0.00382) ≈ 99.62
```

A single cyclic symbol out of 1310 total results in a score of 99.62. The cycle exists but its structural impact on the repository is minimal.

### Example B — Moderate cycle presence

```text
Total files:   200
Cyclic files:  10    (5%)
Total symbols: 800
Cyclic symbols: 32   (4%)

FileCycleRatio   = 10 / 200  = 0.050
SymbolCycleRatio = 32 / 800  = 0.040

CycleRatio    = (0.050 + 0.040) / 2 = 0.045
NormalizedRisk = 0.045 / 0.10 = 0.45
CycleHealth    = 100 × (1 − 0.45) = 55.0
```

5% of files and 4% of symbols in cycles yields a score of 55.0 — in the "Noticeable structural complexity" range.

### Example C — Saturated cycle model

```text
Total files:   100
Cyclic files:  20   (20%)
Total symbols: 300
Cyclic symbols: 60  (20%)

FileCycleRatio   = 0.20
SymbolCycleRatio = 0.20

CycleRatio    = 0.20
NormalizedRisk = min(0.20 / 0.10, 1) = min(2.0, 1) = 1.0
CycleHealth    = 100 × (1 − 1.0) = 0.0
```

20% cyclic nodes saturates the model. The metric reports 0.0, its minimum. Any further increase in cycle ratio does not decrease the score further — the model has already communicated maximum cycle risk.

---

## Interpreting the Score

| Score Range | What It Typically Means |
|-------------|------------------------|
| 95 – 100 | Effectively cycle-free. Any existing cycles are extremely rare edge cases. |
| 80 – 95  | Very few cycles. The occasional cycle may exist but is structurally isolated. |
| 50 – 80  | Moderate cycle presence. Worth investigating which specific files/symbols are involved. |
| 20 – 50  | High cycle prevalence. Refactoring to break cycles should be a priority. |
| 0 – 20   | Extreme cycle density. The dependency graph cannot be meaningfully ordered. |

---

## Why File and Symbol Cycles Are Averaged, Not Summed

Summing file and symbol ratios would be misleading because:

- A repository with 0% file cycles and 8% symbol cycles would report `CycleRatio = 0.08` under averaging, but `0.08` under summation — the same.
- But a repository with 5% file cycles and 5% symbol cycles would report `CycleRatio = 0.05` under averaging, but `0.10` under summation — double the cycle risk from what either individual ratio suggests.

Averaging treats the two ratios as two independent perspectives on the same repository's cycle health, each contributing equally. Summing would amplify the combined risk in a way that is not proportional to either individual signal.

---

## Calibration Parameter

The calibration reference `0.10` (10%) controls the sensitivity of the cycle score:

- A smaller reference (e.g. `0.05`) would make the score decrease faster — a 5% cycle ratio would already reach 0.
- A larger reference (e.g. `0.20`) would make the score more lenient — the score would still be 50 at 10% cycle ratio.

The current value of 10% is CodeGraph's current empirical choice. It can be adjusted in `calculateCycleHealth.ts` as CodeGraph is evaluated against more repositories.
