# 7.8 Dead Code Detection ★

## Status

> ❌ **Not implemented natively in V1.**
> ✅ **V1 decision: External tooling integration — primary candidate: Knip.**

---

## What Was the Original Goal?

Identify code that is structurally present in a JS/TS repository but **not actually reachable or used** — unused files, unreachable functions, unexported symbols, etc.

The naive approach seemed straightforward:

```
Entry Point(s)
      ↓
Graph Traversal
      ↓
Reachable Nodes
      ↓
Unreachable Nodes  ←  Potential Dead Code
```

Walk the graph forward from known entry points. Everything not reached = dead.

---

## Why This Doesn't Work: The Entry Point Problem

The core blocker is that **there is no universal rule for what counts as an entry point**.

JS/TS applications span many execution models:

| Application Type | Entry Point Pattern |
|-----------------|---------------------|
| Express server | `server.js`, `app.ts` |
| Next.js app | Framework-resolved page files, API routes |
| React SPA | `index.tsx` mounting `<App />` |
| CLI tool | `bin/` script |
| Worker process | Custom launch file |
| Library / package | Exports listed in `package.json#exports` |
| Monorepo | Multiple independent roots |

You cannot write a single rule like **"index.ts is the entry point"** or **"a file named server.js is the entry point"** — it depends entirely on the application.

### The Framework Wiring Problem

Frameworks add another layer of indirection. A symbol can be **in active use** without any static `CALLS` edge pointing to it:

```
Express:
  router.get("/path", myController.handle)
    ↑ registered, not called directly by any symbol in the graph

React/Next.js:
  export default function Page() {...}
    ↑ consumed by the framework runtime, not by any internal CALLS edge
```

A simplistic check — *"no node has a CALLS edge to this symbol"* — would flag these as dead code. They are not.

---

## Why `package.json` Entry Points Are Not Enough

One improvement considered was deriving entry points from `package.json`:

```
package.json
      ↓
scripts / main / exports fields
      ↓
entry file
      ↓
traverse from there
```

This helps identify a starting file, but it does not solve the framework wiring problem. Even with a correct root file, the graph traversal will miss symbols that are registered through runtime APIs, not through direct function calls.

**package.json metadata narrows the problem; it does not eliminate it.**

---

## Why It Was Kept Out of the Native Analytics Engine

CodeGraph's graph is a **structural fact graph**. It records what is statically observable:

```
CALLS  ·  IMPORTS  ·  EXPORTS  ·  EXTENDS  ·  IMPLEMENTS  ·  INSTANTIATES
```

Every existing native analyzer (7.1–7.7) operates on these canonical, deterministic facts and produces deterministic results.

Dead-code detection requires **semantic assumptions** that go beyond the current graph:

- What counts as an application entry point?
- Which exports are consumed externally (i.e., the file is a library)?
- Which symbols are invoked by framework runtime wiring?
- Which code is dynamically required/loaded at runtime?

Adding a `DeadCodeAnalyzer` without encoding these semantics would produce **false positives** — legitimately used code classified as dead because its callers are the framework runtime, not a static `CALLS` edge.

> The decision: **do not ship a native analyzer that would lie to the user.**

---

## V1 Architecture Decision

Dead Code Detection is handled as an **external tooling integration**, not a native graph algorithm.

```
CodeGraph                           External Dead-Code Analysis
────────────────────                ────────────────────────────
Parser                              Knip (primary)
GraphBuilder                        ts-prune (narrower alternative)
Canonical Graph
Native Analytics (7.1–7.7)
```

These are separate, parallel concerns. CodeGraph is responsible for structural graph intelligence. Knip is responsible for application- and framework-aware dead-code detection, which it handles using its own broader project semantics.

---

## How This Relates to CodeGraph's Own Reachability

This decision does **not** make CodeGraph's traversal capabilities irrelevant.

| Question | CodeGraph can answer? |
|----------|----------------------|
| What depends on this symbol? | ✅ ImpactAnalyzer |
| What does this symbol depend on? | ✅ DependencyAnalyzer |
| Is there a call chain from A to B? | ✅ CallPathAnalyzer |
| Are there circular dependencies? | ✅ CycleAnalyzer |
| **Is this code truly unused by the application?** | ❌ — requires external tooling |

The distinction is:

```
Structural Reachability   →  deterministic graph question  →  native CodeGraph
Dead Code Detection       →  semantic + framework-aware    →  external tooling
```

---

## What Is Explicitly NOT Being Added

To avoid scope creep justified only by wanting a native dead-code implementation:

- No `DeadCodeAnalyzer` class in `analytics/`
- No new graph relationship types (`REFERENCES`, `READS`, `WRITES`, `TYPE_REFERENCES`) added solely for this purpose
- No heuristic entry-point guessing logic

---

## Future Integration Path

When dead-code results are surfaced in CodeGraph's UI, the intended flow is:

```
Repository
      ↓
CodeGraph pipeline  (parse → build graph → native analysis)
      ↓
External tool  (Knip)
      ↓
Tool output normalized into CodeGraph's API/domain model
      ↓
Frontend displays alongside native graph analyses
```

The external tool results remain clearly **distinguishable** from native graph-based findings. The integration layer's job is normalization and presentation — not re-implementing Knip's logic inside CodeGraph.

## Summary

| Aspect | Decision |
|--------|----------|
| Native `DeadCodeAnalyzer`? | ❌ Not in V1 |
| Why? | Entry point ambiguity + framework runtime wiring = false positives |
| `package.json` entry discovery? | Considered, insufficient on its own |

| V1 approach | External tooling integration |
| Primary tool | **Knip** |
| Alternative | ts-prune (narrower scope) |
