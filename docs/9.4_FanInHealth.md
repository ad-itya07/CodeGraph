# 9.4 Fan-in Health

## What Question Does This Answer?

> **"Are there nodes in this repository that many other nodes depend on, and how concentrated is that inbound dependency load?"**

More specifically: *"When we look at how many incoming edges each file and symbol has, does the graph contain a small number of heavily depended-upon hub nodes that represent critical chokepoints?"*

Fan-in measures the **incoming connectivity** of nodes. A node's fan-in is the count of edges that arrive at it from other nodes — how many things import it, call it, extend it, instantiate it, or otherwise point to it.

Fan-in is the fourth most heavily weighted metric (14%). High fan-in is architecturally significant because:

1. A node with high fan-in is a **shared dependency** — many other components rely on it.
2. Changing such a node's interface, behavior, or semantics can cause ripple effects across all its callers/importers.
3. High fan-in nodes are often the hardest to refactor safely.
4. They represent single points of architectural coupling — if they break, everything that depends on them breaks.

Fan-in receives slightly less weight than fan-out because:

- Depending on something is generally safer than having many things depend on you.
- A library utility that is imported from many files is expected and desirable; the risk is in changing it, not in using it.
- High fan-in is a concentration risk, but it is more predictable and controllable than the unbounded outward surface of a high-fan-out node.

| Field | Type | Description |
|-------|------|-------------|
| `score` | `number` | Normalized health score, 0–100. Higher is healthier. |
| `averageFanIn` | `number` | Mean incoming edge count across all relevant nodes. |
| `rootMeanSquareFanIn` | `number` | RMS of incoming edge counts. Used as the primary input to the health formula. |
| `highestFanIn` | `number` | The highest fan-in observed for any single relevant node. Identifies the most-depended-upon node. |

## What "Fan-in" Means

For a single node $n$, its fan-in is:

$$
\text{FanIn}(n) = |\text{IncomingEdges}(n)|
$$

This is the count of edges arriving at the node, regardless of relationship kind.

### ASCII illustration

```
A ──┐
B ──┤
C ──┼──► D
E ──┘
```

Node `D` has a fan-in of 4. Nodes A, B, C, E have a fan-in of 0 (no incoming edges shown here).

`D` is an architectural hub — four other nodes directly depend on it.

## Raw Measurements

```ts
let totalFanIn   = 0;
let squaredFanIn = 0;
let highestFanIn = 0;

for (const nodeId of nodeIds) {
    const fanIn = graph.incomingEdges.get(nodeId)?.size ?? 0;

    totalFanIn   += fanIn;
    squaredFanIn += fanIn * fanIn;
    highestFanIn  = Math.max(highestFanIn, fanIn);
}
```

### Average fan-in

$$
\text{AverageFanIn} = \frac{\sum_{n} \text{FanIn}(n)}{N}
$$

The arithmetic mean of all incoming degrees.

### Root Mean Square fan-in

$$
\text{RMS}_{\text{FanIn}} = \sqrt{\frac{\sum_{n} \text{FanIn}(n)^2}{N}}
$$

As with fan-out, squaring amplifies the effect of highly-depended-upon nodes.

### Highest fan-in

$$
\text{HighestFanIn} = \max_{n} \text{FanIn}(n)
$$

The single node with the most incoming edges. Not used in the score, but valuable for the user interface to identify and display the most critical dependency hubs.

---

## Why RMS for Fan-in?

The same reasoning applies as for fan-out (see 9.3): the arithmetic mean can hide extreme outliers.

Consider a large repository where most symbols have 0–1 incoming edges, but one utility module is imported by 200 files. The average fan-in might be 0.2 (nearly invisible), while the RMS is meaningfully elevated, reflecting the architectural exposure of that single shared module.

$$
\text{Example:}
$$

```text
999 nodes with fanIn = 0
1 node  with fanIn = 200

Average = 200 / 1000 = 0.2
RMS     = sqrt(200² / 1000) = sqrt(40000 / 1000) = sqrt(40) ≈ 6.32
```

The single shared node with fan-in 200 barely registers in the average, but it raises the RMS to 6.32 — clearly signaling the architectural concentration.

---

## Normalization

### Calibration factor

$$
F_{\text{fanIn}} = 0.5
$$

### Normalized risk

$$
\text{NormalizedRisk} = F_{\text{fanIn}} \times \text{RMS}_{\text{FanIn}}
$$

### Health score

$$
\text{FanInHealth} = \frac{100}{1 + 0.5 \times \text{RMS}_{\text{FanIn}}}
$$

This uses the same **reciprocal normalization** as coupling and fan-out.

---

## Score Behavior Table

| RMS FanIn | NormalizedRisk | FanInHealth |
|----------|---------------|------------|
| 0.0 | 0.00 | 100.0 |
| 0.5 | 0.25 | 80.0 |
| 1.0 | 0.50 | 66.7 |
| 2.0 | 1.00 | 50.0 |
| 4.0 | 2.00 | 33.3 |
| 8.0 | 4.00 | 20.0 |

The formula is identical to fan-out normalization. The difference in practical scores between fan-in and fan-out comes entirely from the difference in their raw distributions — not from any difference in the normalization formula.

## Full Implementation

```ts
const FAN_IN_FACTOR = 0.5;

export function calculateFanInHealth(graph: Graph): FanInHealthResult {
    const nodeIds = [
        ...(graph.nodesByKind.get("file")   ?? new Set<string>()),
        ...(graph.nodesByKind.get("symbol") ?? new Set<string>()),
    ];

    if (nodeIds.length === 0) {
        return { score: 100, averageFanIn: 0, rootMeanSquareFanIn: 0, highestFanIn: 0 };
    }

    let totalFanIn   = 0;
    let squaredFanIn = 0;
    let highestFanIn = 0;

    for (const nodeId of nodeIds) {
        const fanIn = graph.incomingEdges.get(nodeId)?.size ?? 0;

        totalFanIn   += fanIn;
        squaredFanIn += fanIn * fanIn;
        highestFanIn  = Math.max(highestFanIn, fanIn);
    }

    const averageFanIn        = totalFanIn / nodeIds.length;
    const rootMeanSquareFanIn = Math.sqrt(squaredFanIn / nodeIds.length);
    const normalizedRisk      = FAN_IN_FACTOR * rootMeanSquareFanIn;
    const score               = 100 / (1 + normalizedRisk);

    return { score, averageFanIn, rootMeanSquareFanIn, highestFanIn };
}
```

## Worked Examples

### Example A — Flat, distributed usage

```text
Total nodes: 1000
FanIn distribution: all nodes have fanIn between 0 and 1

squaredFanIn ≈ 500 (half have fanIn=1, half have fanIn=0)
averageFanIn = 0.5
RMS FanIn    = sqrt(500 / 1000) = sqrt(0.5) ≈ 0.707
normalizedRisk = 0.5 × 0.707 = 0.354
FanInHealth    = 100 / 1.354 ≈ 73.9
```

Very flat fan-in distribution — no hubs, evenly distributed usage. Score in the 70s.

### Example B — One dominant hub (realistic library pattern)

```text
Total nodes: 28000
All nodes have fanIn = 0 except:
  - 1 node has fanIn = 344

squaredFanIn = 344² = 118336
averageFanIn        = 344 / 28000 ≈ 0.0123
RMS FanIn           = sqrt(118336 / 28000) ≈ sqrt(4.226) ≈ 2.056
normalizedRisk      = 0.5 × 2.056 = 1.028
FanInHealth         = 100 / 2.028 ≈ 49.3
```

A single node with fan-in 344 (imported by 344 other nodes) pulls the score down to 49 — even though the average fan-in is only 0.012. This reflects the genuine architectural significance of that hub node.

### Example C — Typical medium-sized repository

```text
Total nodes: 1310 (files + symbols)
RMS FanIn = 0.344

normalizedRisk = 0.5 × 0.344 = 0.172
FanInHealth    = 100 / 1.172 ≈ 85.3
```

Moderate RMS fan-in reflects a typical medium repository where most nodes have low incoming degree, but a few are moderately shared. Score of 85.3 — generally healthy.

---

## Interpreting the Score in Context

| FanInHealth | What It Typically Means |
|-------------|------------------------|
| 85 – 100 | Very low RMS fan-in. The graph has no dominant hubs. |
| 70 – 85  | Moderate fan-in. Some nodes are shared, but nothing extreme. |
| 50 – 70  | Elevated fan-in. Some nodes are heavily used — may be acceptable if they are stable interfaces. |
| 30 – 50  | High fan-in concentration. A small number of nodes are shared widely. Changes to them are high-risk. |
| 0 – 30   | Extreme fan-in concentration. The architecture has critical hub nodes with very high dependency loads. |

---

## Contrast with Fan-out

| Metric | Measures | High value means |
|--------|----------|-----------------|
| Fan-out | Outgoing edges | This node depends on many things |
| Fan-in | Incoming edges | Many things depend on this node |

A node can be high in one and not the other:

- **High fan-out, low fan-in**: A "leaf orchestrator" — it pulls many dependencies together but nothing depends on it. Example: a top-level API handler.
- **Low fan-out, high fan-in**: A stable utility — many things use it but it depends on very little. Example: a string formatting module.
- **High fan-out and high fan-in**: An "integration hub" — architecturally dangerous because it both depends on much and is depended on by much.
- **Low fan-out and low fan-in**: A leaf node — nearly isolated. Structurally safe, potentially dead code.

---

## Calibration Parameter

The `0.5` factor has the same interpretation as in fan-out:

$$
\text{FanIn} = 2 \Rightarrow \text{Health} = \frac{100}{1 + 0.5 \times 2} = 50
$$

The "50% health" threshold is at RMS fan-in = 2.
