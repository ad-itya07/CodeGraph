# 7.1 Graph Traversal

## What Question Does This Answer?

> **"Starting from node X, which nodes can I reach by following edges in direction D, restricted to relationship kinds R, and at most N hops away?"**

`GraphTraversal` is not an analyzer in the product sense — it does not answer a user-visible question by itself. It is the **graph-walking primitive** that all higher-level analyzers that need multi-hop reachability build on. It encapsulates Breadth-First Search (BFS) over the `Graph` so that no other class has to re-implement it.

## Class Signature

```ts
class GraphTraversal {
    constructor(private readonly graph: Graph) {}

    traverse(startNodeId: string, options: TraversalOptions): TraversalResult
}
```

### Input: `TraversalOptions`

```ts
interface TraversalOptions {
    direction: "outgoing" | "incoming";
    relationshipKinds?: RelationshipKind[];
    maxDepth?: number;
}
```

| Field | Type | Required | Meaning |
|-------|------|----------|---------|
| `direction` | `"outgoing" \| "incoming"` | ✅ | Which direction to follow edges. `"outgoing"` follows edges away from the node (the node is the source); `"incoming"` follows edges toward the node (the node is the target). |
| `relationshipKinds` | `RelationshipKind[]` | ❌ | If supplied, only edges whose `relationshipKind` is in this list will be followed. If omitted, all edge kinds are traversed. |
| `maxDepth` | `number` | ❌ | Maximum number of hops from the start node. If omitted, traversal continues until all reachable nodes are visited. |

### Output: `TraversalResult`

```ts
interface TraversalResult {
    startNodeId: string;
    nodes: string[];
    depthByNode: Map<string, number>;
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `startNodeId` | `string` | The node the traversal started from (echoed back for convenience). |
| `nodes` | `string[]` | IDs of every node reached during traversal, **excluding** the start node itself. Ordered by discovery (BFS order — breadth-first, not sorted). |
| `depthByNode` | `Map<string, number>` | Maps each reached node ID to how many hops away from `startNodeId` it was found. The start node itself is not in this map. |

## Algorithm: Iterative BFS

### Why BFS?

BFS is chosen over DFS for two reasons:

1. **Natural depth tracking.** Because BFS expands layer by layer, a node's depth is simply the depth of its parent plus one. This makes `depthByNode` trivially accurate without extra bookkeeping.
2. **Shortest-distance guarantee.** If a node is reachable via multiple paths, BFS guarantees the first time it is encountered corresponds to the *shortest* path. This is important for the `ImpactAnalyzer` and `DependencyAnalyzer` — the `depthByNode` they expose reflects the minimum number of hops, which is the semantically correct distance.

### Internal Queue Item

```ts
interface TraversalQueueItem {
    nodeId: string;
    depth: number;
}
```

The queue carries both the node ID and its current depth so that the depth cutoff check is O(1) per node.

### Step-by-Step Walkthrough

```
Input: startNodeId = "A", direction = "outgoing", maxDepth = 2, no filter

Graph edges (outgoing):
  A → B (calls)
  A → C (imports)
  B → D (calls)
  B → E (extends)
  D → F (calls)

Step 1: Initialize
  visited = { A }
  queue   = [ {A, depth:0} ]
  nodes   = []

Step 2: Dequeue {A, depth:0}
  depth 0 < maxDepth 2, so process
  outgoing edges from A: B (calls), C (imports)
  B not visited → add to visited, push {B, depth:1}, nodes=[B]
  C not visited → add to visited, push {C, depth:1}, nodes=[B,C]
  queue = [ {B,1}, {C,1} ]

Step 3: Dequeue {B, depth:1}
  depth 1 < maxDepth 2, so process
  outgoing edges from B: D (calls), E (extends)
  D not visited → add, push {D,2}, nodes=[B,C,D]
  E not visited → add, push {E,2}, nodes=[B,C,D,E]
  queue = [ {C,1}, {D,2}, {E,2} ]

Step 4: Dequeue {C, depth:1}
  depth 1 < maxDepth 2, so process
  No outgoing edges from C.

Step 5: Dequeue {D, depth:2}
  depth 2 >= maxDepth 2 → SKIP (continue, do not expand)

Step 6: Dequeue {E, depth:2}
  depth 2 >= maxDepth 2 → SKIP

Result:
  nodes        = ["B", "C", "D", "E"]
  depthByNode  = { B:1, C:1, D:2, E:2 }
  (F is never reached because D was not expanded)
```

### Depth Cutoff Implementation Detail

```ts
if (options.maxDepth !== undefined && current.depth >= options.maxDepth) continue;
```

The check is `>= maxDepth`, not `> maxDepth`. This means a node *at* `maxDepth` is **added to the result** (when its parent is processed at `maxDepth - 1`) but its own neighbors are **not explored**. So `maxDepth: 1` gives you only the immediate neighbors of the start node.

### Edge Direction Switching

```ts
const edgeIds =
    options.direction === "outgoing"
        ? this.graph.outgoingEdges.get(current.nodeId)
        : this.graph.incomingEdges.get(current.nodeId);
```

The `Graph` pre-indexes edges in both directions (`outgoingEdges` and `incomingEdges` are both `Map<string, Set<string>>`). Switching direction is just a matter of choosing the correct index — the edge objects themselves are the same.

When traversing **incoming**, the "next" node is `edge.sourceId` (the node that points *to* the current node), not `edge.targetId`.

```ts
const nextNodeId =
    options.direction === "outgoing"
        ? edge.targetId
        : edge.sourceId;
```

### Relationship Kind Filtering

```ts
if (
    options.relationshipKinds &&
    !options.relationshipKinds.includes(edge.relationshipKind)
) continue;
```

Filtering happens inside the edge loop, after retrieving the edge object. Because the `Graph` does not maintain separate indexes per relationship kind, the filter is O(|E|) in the worst case over the subgraph being explored. This is acceptable because the number of edges per node is small in practice for a TypeScript codebase.

---

## Implementation Choices and Trade-offs

### Iterative BFS, Not Recursive DFS

The implementation uses an **array-as-queue** with a `queueIndex` pointer rather than `shift()`:

```ts
let queueIndex = 0;
while (queueIndex < queue.length) {
    const current = queue[queueIndex++];
    // ...
}
```

`Array.shift()` in JavaScript is O(n) because it shifts every element left. Using an index pointer makes dequeue O(1), which matters for large graphs where thousands of nodes may be explored.

### Start Node Excluded from Result

The start node is added to `visited` before the loop but is never pushed to `nodes`. This is an intentional contract: callers (like `ImpactAnalyzer`) want to know *other* nodes that are affected, not the source node itself. Including the source would require callers to filter it out every time.

### No Edge Following for Start Node at Depth Limit

Nodes exactly at `maxDepth` are added to `nodes` and `depthByNode` but are not expanded. This is the most intuitive behavior: `maxDepth: 2` means "show me everything reachable in at most 2 hops", and nodes at hop 2 are included as destinations.

## Usage by Other Analyzers

```ts
// ImpactAnalyzer — who depends on me? (walk backward)
this.traversal.traverse(sourceNodeId, {
    direction: "incoming",
    relationshipKinds: ["calls", "imports", "extends", "implements", "instantiates"],
    maxDepth: options.maxDepth,
});

// DependencyAnalyzer — what do I depend on? (walk forward)
this.traversal.traverse(sourceNodeId, {
    direction: "outgoing",
    relationshipKinds: ["calls", "imports", "extends", "implements", "instantiates"],
    maxDepth: options.maxDepth,
});
```

Both analyzers use identical `relationshipKinds` filters — only structural relationships are followed (not `"exports"` or `"references"`, which are not load-bearing dependency edges).
