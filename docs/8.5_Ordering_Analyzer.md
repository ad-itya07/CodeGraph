# 7.5 Ordering Analyzer

## What Question Does This Answer?

> **"In what order should the symbols that X depends on be initialized or processed so that each symbol is ready before anything that depends on it?"**

Equivalently: *"What is a valid topological ordering of X's dependency subgraph?"*

This is the classic **dependency-first ordering** problem: given a set of symbols where some depend on others, produce a sequence where a symbol only appears after all of its own dependencies have already appeared. This is the order in which you would need to define, initialize, or process symbols in a dependency-correct way.

An important secondary output: if `isOrderable` is `false`, it means the subgraph contains a cycle, which means no valid linear ordering exists.

### Concrete Example

```
Symbols and their dependencies:
  App       → depends on → Router, Database
  Router    → depends on → MiddlewareStack
  Database  → depends on → ConnectionPool
  ConnectionPool  (no dependencies)
  MiddlewareStack (no dependencies)
```

A valid topological order (dependency-first) would be:
```
orderedNodeIds = [
    "ConnectionPool",
    "MiddlewareStack",
    "Database",
    "Router",
    "App",
]
```

`ConnectionPool` and `MiddlewareStack` have no dependencies, so they come first. `Database` and `Router` come next (their own dependencies are already listed). `App` comes last.

## Algorithm: Two-Phase Approach — Iterative DFS Collection + Kahn's Topological Sort

The analysis runs in two distinct phases.

### Phase 1: Collect the Dependency Subgraph

Before sorting, the analyzer must know *which* nodes to include. It runs an iterative DFS from `sourceNodeId` following only **symbol → symbol** dependency edges:

```ts
const dependencyRelationshipKinds = new Set([
    "calls",
    "extends",
    "implements",
    "instantiates",
    // Note: "imports" is intentionally excluded
]);
```

**Why is `"imports"` excluded here?**

`"imports"` edges connect **file nodes** to other **file nodes**. The Ordering Analyzer is a symbol-level tool — it answers questions about symbol initialization order, not file load order. The collection phase explicitly filters to `targetNode.kind === "symbol"`, so file nodes would be discarded anyway. Excluding `"imports"` avoids unnecessary edge lookups.

```ts
private collectDependencies(sourceNodeId: string): string[] {
    const visited = new Set<string>([sourceNodeId]);
    const stack   = [sourceNodeId];
    const dependencies: string[] = [];

    while (stack.length > 0) {
        const currentNodeId = stack.pop()!;
        for each outgoing edge of currentNodeId:
            if edge.relationshipKind not in dependencyRelationshipKinds → skip
            if targetNode.kind !== "symbol" → skip
            if already visited → skip
            
            visited.add(targetId)
            dependencies.push(targetId)
            stack.push(targetId)
    }

    return dependencies;
}
```

This gives a flat list of all symbol node IDs that are reachable from `sourceNodeId` via dependency edges (the exact same set `DependencyAnalyzer` would return if queried without a depth limit, filtered to symbols only).

### Phase 2: Kahn's Algorithm for Topological Sort

Kahn's algorithm produces a topological ordering by repeatedly removing nodes with no remaining dependencies (indegree 0 in the dependency graph).

#### The Conceptual Inversion

Here is the key conceptual insight of this implementation, documented explicitly in the source code:

> In CodeGraph, `A → B` means **A depends on B** (A calls B, A extends B, etc.).
> For dependency-first ordering, we need B to come *before* A.
> The ordering graph is therefore the conceptual *reverse*: `B → A`.
>
> In this reversed perspective, a node's **indegree** represents:
> **"How many of my dependencies still haven't been processed yet?"**
>
> A node with indegree 0 has all its dependencies already emitted — it is safe to emit next.

#### Computing Indegrees

The `relevantNodeIds` set is `{ sourceNodeId } ∪ { all collected dependencies }`.

```ts
const indegree = new Map<string, number>();
for each nodeId in relevantNodeIds: indegree.set(nodeId, 0);

for each nodeId in relevantNodeIds:
    for each outgoing edge of nodeId (dependency edge):
        if targetId is in relevantNodeIds:
            // nodeId → targetId means nodeId depends on targetId
            // In ordering graph: targetId must come first, so nodeId's indegree += 1
            indegree.set(nodeId, indegree.get(nodeId)! + 1);
```

The indegree of a node = the number of its direct dependencies that are part of the subgraph. Nodes with `indegree === 0` have no dependencies in the subgraph — they can be emitted first.

#### The Kahn's BFS Loop

```
Initial queue: all nodes where indegree === 0

while queue is not empty:
    nodeId = dequeue
    emit nodeId → orderedNodeIds.push(nodeId)

    for each node that depends on nodeId (incoming edges in the original graph):
        if that node is in relevantNodeIds:
            reduce its indegree by 1
            if its indegree is now 0: add to queue
```

The "find nodes that depend on nodeId" step uses `graph.incomingEdges.get(nodeId)` — these are nodes where `edge.sourceId` has `nodeId` as a dependency. Reducing their indegree simulates "nodeId has been processed, one fewer dependency blocking them."

#### Cycle Detection via Kahn's

Kahn's algorithm naturally detects cycles:

```ts
isOrderable: orderedNodeIds.length === relevantNodeIds.size
```

If a cycle exists, the nodes in the cycle will never reach `indegree === 0` (they all mutually block each other), so they will never be enqueued. The final `orderedNodeIds` will be shorter than `relevantNodeIds`, and `isOrderable` will be `false`.

### Step-by-Step Trace

```
Input: sourceNodeId = "App"

Subgraph after Phase 1 collection:
  relevantNodeIds = { App, Router, Database, ConnectionPool, MiddlewareStack }

Indegree computation (who depends on whom):
  App → Router        → indegree[App]++
  App → Database      → indegree[App]++
  Router → Middleware → indegree[Router]++
  Database → ConnPool → indegree[Database]++

  indegree = { App:2, Router:1, Database:1, ConnectionPool:0, MiddlewareStack:0 }

Kahn's loop:
  Queue = [ConnectionPool, MiddlewareStack]  (indegree === 0)

  Emit ConnectionPool
    Nodes that depend on ConnectionPool: Database
    indegree[Database] = 1 - 1 = 0 → enqueue Database
  Queue = [MiddlewareStack, Database]

  Emit MiddlewareStack
    Nodes that depend on MiddlewareStack: Router
    indegree[Router] = 1 - 1 = 0 → enqueue Router
  Queue = [Database, Router]

  Emit Database
    Nodes that depend on Database: App
    indegree[App] = 2 - 1 = 1 → NOT enqueued yet
  Queue = [Router]

  Emit Router
    Nodes that depend on Router: App
    indegree[App] = 1 - 1 = 0 → enqueue App
  Queue = [App]

  Emit App
  Queue = []

orderedNodeIds = [ConnectionPool, MiddlewareStack, Database, Router, App]
isOrderable    = true (5 emitted == 5 in subgraph)
```

## Design Notes

**Source node appears last**: By construction, the source node's indegree equals the number of its direct dependencies that are in the subgraph. It is always emitted last (or near-last if some dependencies are not reachable). This is correct: in dependency-first order, the entry point is the last thing initialized.

**Only symbol nodes**: The analyzer explicitly skips any edge target that is not a `"symbol"` node. File nodes, dependency nodes, and module nodes are not part of symbol-level initialization ordering.

**`isOrderable` as a cycle indicator**: While the Cycle Analyzer (`7.4`) detects and returns the actual cycle groups, the Ordering Analyzer's `isOrderable` field provides the same information in a compact form for the specific subgraph of `sourceNodeId`. If `isOrderable: false`, consult the Cycle Analyzer for the detailed cycle membership.
