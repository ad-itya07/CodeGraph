# 7.3 Dependency Analyzer

## What Question Does This Answer?

> **"What does symbol X depend on, directly or transitively?"**

Equivalently: *"What does X need to exist and function correctly?"* or *"Which nodes are downstream of X?"*

The Dependency Analyzer walks **forward** through the graph — following the direction of the edges — to find every node that X has a structural dependency on. This is the forward-reachability mirror of the Impact Analyzer.

### Concrete Example

Given the same call graph:

```
AuthService.login → TokenService.generate → CryptoUtil.sign
                                           → CryptoUtil.hash
UserController.register → AuthService.login
```

If you ask for the dependencies of `AuthService.login`:

```
dependencyNodeIds = [
    "TokenService.generate",   // depth 1 — directly called
    "CryptoUtil.sign",         // depth 2 — called by TokenService.generate
    "CryptoUtil.hash",         // depth 2 — called by TokenService.generate
]
```

This tells you: if you want to understand, test, or run `AuthService.login` in isolation, you also need `TokenService.generate`, `CryptoUtil.sign`, and `CryptoUtil.hash`.

## Class Signature

```ts
class DependencyAnalyzer {
    constructor(private readonly traversal: GraphTraversal) {}

    analyze(sourceNodeId: string, options: DependencyAnalysisOptions): DependencyAnalysisResult
}
```

### Input

```ts
// Parameter
sourceNodeId: string   // The node whose dependencies you want

// Options
interface DependencyAnalysisOptions {
    maxDepth?: number;
}
```

| Parameter | Type | Required | Meaning |
|-----------|------|----------|---------|
| `sourceNodeId` | `string` | ✅ | The node you are inspecting. The analyzer will find everything this node depends on. |
| `maxDepth` | `number` | ❌ | Maximum number of hops to traverse forward. Omitting it gives the full transitive dependency closure. `1` gives only direct dependencies. |

### Output

```ts
interface DependencyAnalysisResult {
    sourceNodeId: string;
    dependencyNodeIds: string[];
    depthByNode: Map<string, number>;
}
```

| Field | Type | Meaning |
|-------|------|---------|
| `sourceNodeId` | `string` | Echoed back for traceability. |
| `dependencyNodeIds` | `string[]` | IDs of all nodes that `sourceNodeId` depends on. Ordered by BFS discovery (nearest first). |
| `depthByNode` | `Map<string, number>` | For each dependency, how many hops away it is. Depth 1 = direct dependency; depth 2 = dependency of a direct dependency; etc. |

## Algorithm

Like `ImpactAnalyzer`, `DependencyAnalyzer` is a thin wrapper over `GraphTraversal`:

```ts
analyze(sourceNodeId: string, options: DependencyAnalysisOptions = {}): DependencyAnalysisResult {
    const traversalResult = this.traversal.traverse(sourceNodeId, {
        direction: "outgoing",       // ← Walk forward (along edge direction)
        relationshipKinds: [
            "calls",
            "imports",
            "extends",
            "implements",
            "instantiates",
        ],
        maxDepth: options.maxDepth,
    });

    return {
        sourceNodeId,
        dependencyNodeIds: traversalResult.nodes,
        depthByNode: traversalResult.depthByNode,
    };
}
```

### Why `direction: "outgoing"`?

An edge `A → B` means A depends on B. To find what A depends on, follow the outgoing edges of A — the `edge.targetId` at each hop is the thing A (or A's dependency) is consuming. The traversal engine resolves this by consulting `graph.outgoingEdges.get(currentNodeId)` and following `edge.targetId`.

### Why These Specific `relationshipKinds`?

These are identical to `ImpactAnalyzer` and for the same reasons:

| Kind | Why it represents a real dependency |
|------|-------------------------------------|
| `calls` | If A calls B, A has a behavioral dependency on B. |
| `imports` | If file A imports file B, A has a load-time dependency on B. |
| `extends` | If A extends B, A has a structural dependency on B's definition. |
| `implements` | If A implements B, A has a contract dependency on B's interface shape. |
| `instantiates` | If A does `new B(...)`, A has a construction dependency on B. |

---

## Contrast with `ImpactAnalyzer`

| | `DependencyAnalyzer` | `ImpactAnalyzer` |
|---|---|---|
| **Question** | What does X need? | Who needs X? |
| **Edge direction** | Outgoing (forward) | Incoming (backward) |
| **Result set** | X's dependency subtree | X's consumer supertree |
| **Use case** | Bundling, testing isolation, understanding coupling | Change impact analysis, refactoring safety |

Both analyzers produce results with depth information, which lets callers prioritize: direct dependencies (depth 1) are the most immediately relevant; deep transitive ones (large depth) are the most indirect.

---

## Use Cases

1. **Test isolation** — to unit-test a function in isolation, mock everything in its `dependencyNodeIds` at depth 1.
2. **Bundle analysis** — to understand what code must be included to ship a specific entry point.
3. **Coupling measurement** — the size of `dependencyNodeIds` (its cardinality, without a `maxDepth` limit) is a direct proxy for how deeply coupled a symbol is.
4. **Visualisation** — the `depthByNode` map is the data source for rendering a radial dependency tree in the CodeGraph UI.
