# 9.6 Module Health

## What Question Does This Answer?

> **"What proportion of the total graph nodes are module nodes, and does that proportion suggest an unusual graph structure?"**

More specifically: *"When CodeGraph builds the repository's graph, what fraction of all graph nodes are classified as 'module' nodes rather than file, symbol, or dependency nodes?"*

Module Health is the lowest-weighted metric in the Health Index (7%). Its role is not to capture a primary architectural concern, but to provide a structural signal about the **completeness and composition of the graph itself**.

Module nodes represent module-level graph entities — they appear when CodeGraph's resolution process identifies a module-level entity that does not correspond cleanly to a repository file node or a symbol node. Their presence in the graph can indicate:

- External modules or virtual module placeholders that the parser created during resolution.
- Non-file module boundaries identified during graph construction.
- Gaps in the file-level graph representation where module-level information was present but file information was not.

A graph with very few module nodes (close to 0% of total nodes) is considered structurally clean from a module-representation standpoint. A graph where module nodes represent a significant fraction of total nodes suggests either unusual repository structure or resolution artifacts.

## TypeScript Interface

```ts
export interface ModuleHealthResult {
    score: number;
    moduleCount: number;
    totalNodeCount: number;
    moduleRatio: number;
}
```

| Field | Type | Description |
|-------|------|-------------|
| `score` | `number` | Normalized health score, 0–100. Higher is healthier. |
| `moduleCount` | `number` | Total number of module nodes in the graph. |
| `totalNodeCount` | `number` | Total number of nodes of all kinds in the graph. |
| `moduleRatio` | `number` | `moduleCount / totalNodeCount`. The primary health input. |

---

## What "Module Node" Means in CodeGraph

The CodeGraph graph model supports four node kinds:

| Kind | What It Represents |
|------|-------------------|
| `file` | A repository source file |
| `symbol` | A code symbol (function, class, variable, etc.) |
| `dependency` | An external package/library node |
| `module` | A module-level entity not directly a file or symbol |

Module nodes occupy a special category. They are counted by the health metric as an indicator of graph composition, not of code quality.

---

## Raw Measurement

### Module count

```ts
const moduleCount = graph.nodesByKind.get("module")?.size ?? 0;
```

The total number of nodes whose `kind` is `"module"`.

### Total node count

```ts
const totalNodeCount = graph.nodes.size;
```

The total count of all graph nodes, regardless of kind. This includes files, symbols, dependencies, and modules.

### Module ratio

$$
\text{ModuleRatio} = \frac{\text{ModuleCount}}{\text{TotalNodeCount}}
$$

The denominator includes **all four node kinds**, not just module nodes. This ensures the ratio is always between 0 and 1.

For an empty graph (`totalNodeCount === 0`), the function returns early:

```ts
{ score: 100, moduleCount: 0, totalNodeCount: 0, moduleRatio: 0 }
```

---

## Normalization

Module health uses **linear normalization** — the simplest of the two normalization strategies used in the Health Index.

$$
\text{ModuleHealth} = 100 \times (1 - \text{ModuleRatio})
$$

This is a direct inversion: a module ratio of 0 yields a score of 100, and a module ratio of 1 (all nodes are module nodes, which is pathological) yields a score of 0. The relationship is perfectly linear.

There is no calibration factor or reciprocal function. This is appropriate because:

1. The module ratio is already bounded between 0 and 1 (unlike fan-out, coupling, or fan-in which are unbounded).
2. Module health is a simple structural signal that does not need to penalize outliers disproportionately.

---

## Score Behavior Table

| ModuleRatio | ModuleHealth |
|------------|-------------|
| 0.000 (0%) | 100.0 |
| 0.001 (0.1%) | 99.9 |
| 0.010 (1%) | 99.0 |
| 0.050 (5%) | 95.0 |
| 0.100 (10%) | 90.0 |
| 0.500 (50%) | 50.0 |
| 1.000 (100%) | 0.0 |

In practice, module ratios in well-analyzed repositories are extremely small — typically well below 0.1%. The module health score therefore almost always approaches 100. Its 7% weight means that even a module score of 95 contributes roughly 6.65 out of 7 possible points to the final Health Index.

---

## Full Implementation

```ts
export function calculateModuleHealth(graph: Graph): ModuleHealthResult {
    const moduleCount    = graph.nodesByKind.get("module")?.size ?? 0;
    const totalNodeCount = graph.nodes.size;

    if (totalNodeCount === 0) {
        return { score: 100, moduleCount: 0, totalNodeCount: 0, moduleRatio: 0 };
    }

    const moduleRatio = moduleCount / totalNodeCount;
    const score       = 100 * (1 - moduleRatio);

    return { score, moduleCount, totalNodeCount, moduleRatio };
}
```

This is the simplest of all six metric implementations — no loops, no accumulation, no calibration factor.

## Worked Examples

### Example A — Typical large repository

```text
moduleCount    = 20
totalNodeCount = 28980

moduleRatio   = 20 / 28980 ≈ 0.000690
ModuleHealth  = 100 × (1 − 0.000690) ≈ 99.93
```

20 module nodes among nearly 29,000 total nodes. Module ratio is 0.069% — practically zero. Score is 99.93.

In the final Health Index, this metric contributes:

$$
99.93 \times 0.07 \approx 6.995 \text{ points}
$$

Nearly the full 7 points that module health can contribute.

### Example B — Elevated module presence

```text
moduleCount    = 500
totalNodeCount = 5000

moduleRatio   = 500 / 5000 = 0.100
ModuleHealth  = 100 × (1 − 0.100) = 90.0
```

10% module ratio — unusually high, probably indicating that the repository heavily uses virtual module boundaries or that graph resolution produced many module placeholders. Score of 90.

In the final Health Index, this metric contributes:

$$
90 \times 0.07 = 6.3 \text{ points}
$$

versus the ideal 7.0 — a difference of 0.7 points on the final score.

### Example C — Pathological case

```text
moduleCount    = 2000
totalNodeCount = 2500

moduleRatio   = 2000 / 2500 = 0.800
ModuleHealth  = 100 × (1 − 0.800) = 20.0
```

80% of the graph is module nodes — this would be an extreme and highly unusual case, suggesting that the repository could not be fully parsed into file and symbol nodes. Score of 20.

In the final Health Index, even this extreme case only subtracts:

$$
7.0 - (20 \times 0.07) = 7.0 - 1.4 = 5.6 \text{ points}
$$

Because module health has only a 7% weight, even this worst-case scenario moves the final index by only ~5.6 points. This is by design — module node presence should not dominate the overall repository score.

---

## Why Module Health Has the Lowest Weight

Module node presence is a graph structural artifact, not a primary code quality signal. The reasons for the low 7% weight are:

1. **It rarely changes significantly.** Most repositories have near-zero module ratios. Module health almost always scores near 100.
2. **Its architectural significance is indirect.** A high module ratio reflects something about how CodeGraph's parser and resolution process modeled the repository — not necessarily a flaw in the repository's design.
3. **It is a completeness indicator.** Module health is more useful as a diagnostic signal about the graph's representation than as an architectural quality judgement about the code.
4. **The other five metrics capture the primary structural risks.** Cycles, coupling, and fan metrics address the core architectural health dimensions.

---

## Interpreting the Score in Context

| ModuleHealth | What It Typically Means |
|--------------|------------------------|
| 99 – 100 | Module nodes are negligible (< 1% of graph). Normal and expected. |
| 95 – 99  | Module nodes are very small in proportion (1–5%). Minor graph composition note. |
| 90 – 95  | Module nodes make up 5–10% of the graph. Worth investigating why. |
| 70 – 90  | Module nodes make up 10–30% of the graph. Unusual; may indicate parsing or resolution artifacts. |
| 0 – 70   | Module nodes dominate the graph. The graph may be unrepresentative of the actual file structure. |

---

## Linear vs. Reciprocal Normalization

Module health is one of only two metrics that use **linear normalization** (the other being cycle health for its bounded cycle ratio). The choice of linear vs. reciprocal normalization depends on the range of the input:

| Metric | Input Range | Normalization |
|--------|------------|---------------|
| Cycles | 0–1 (bounded) | Linear (with bounded cap) |
| Module | 0–1 (bounded) | Linear |
| Coupling | 0–∞ (unbounded) | Reciprocal |
| Fan-out | 0–∞ (unbounded) | Reciprocal |
| Fan-in | 0–∞ (unbounded) | Reciprocal |
| Dependency | 0–∞ (unbounded) | Reciprocal |

When the input is already naturally bounded to [0,1], linear normalization is both simpler and more appropriate. When the input is unbounded, reciprocal normalization avoids the need for an arbitrary cap while still producing a score in [0,100].
