# 7.4 Cycle Analyzer

## What Question Does This Answer?

> **"Are there any circular dependencies or mutual recursions in this codebase, and if so, what are they?"**

More specifically: *"Does any group of nodes in the graph form a strongly connected component with more than one node (or a self-loop)?"*

A cycle in a code graph is a situation where node A depends on node B which — through some chain of edges — depends back on node A. Cycles are always structurally problematic because they create tight coupling and make reasoning about load order, testing, and refactoring significantly harder.

### Concrete Examples

**File import cycle** (circular dependency):
```
auth.ts  → imports → user.ts
user.ts  → imports → profile.ts
profile.ts → imports → auth.ts   ← closes the cycle
```
All three files form a cycle of type `"file-import"`.

**Call cycle** (mutual recursion):
```
isEven(n) → calls → isOdd(n-1)
isOdd(n)  → calls → isEven(n-1)
```
These two functions form a cycle of type `"symbol-call"`.

**Self-loop** (direct recursion):
```
factorial → calls → factorial
```
A single-node cycle of type `"symbol-call"`.

## Algorithm: Tarjan's Strongly Connected Components (SCC)

### Why Tarjan's SCC?

Detecting cycles is equivalent to finding **Strongly Connected Components** of size ≥ 2 (or self-loops). Tarjan's algorithm finds all SCCs in a single DFS pass in **O(V + E)** time, where V is the number of nodes and E is the number of edges in the projected subgraph. This is optimal — you cannot find all cycles without examining all reachable edges at least once.

Alternative algorithms like Johnson's (finds every individual cycle path) were not used because:
1. In large codebases, the number of individual cycles can be exponential. Tarjan's gives you the *participating groups*, which is the actionable information.
2. Tarjan's is O(V+E); Johnson's is O((V+E)(C+1)) where C is the number of individual cycles.

### Graph Projections

Before running Tarjan's, the analyzer creates a **logical projection** — a view of the graph restricted to a specific node kind and relationship kind pair:

```ts
const cycleProjections: Record<CycleType, CycleProjection> = {
    "file-import":            { nodeKind: "file",   relationshipKind: "imports"      },
    "symbol-call":            { nodeKind: "symbol", relationshipKind: "calls"        },
    "symbol-inheritance":     { nodeKind: "symbol", relationshipKind: "extends"      },
    "symbol-implementation":  { nodeKind: "symbol", relationshipKind: "implements"   },
    "symbol-instantiation":   { nodeKind: "symbol", relationshipKind: "instantiates" },
};
```

The projection is applied by filtering both nodes (only those with `node.kind === projection.nodeKind`) and edges (only those with `edge.relationshipKind === projection.relationshipKind` and whose target node is of the correct kind).

This is important because a "call cycle" among symbols must not traverse import edges, and an "import cycle" among files must not traverse call edges. Each projection is an independent analysis.

### Tarjan's Algorithm — Data Structures

```ts
const indices  = new Map<string, number>();  // Discovery index per node
const lowLinks = new Map<string, number>();  // Lowest index reachable from subtree
const stack    = string[];                   // Current DFS path
const onStack  = new Set<string>();          // Fast membership test for stack
let   index    = 0;                          // Global discovery counter
```

**`index`** (aka discovery index): A monotonically increasing counter. Every node gets a unique `index` when it is first visited.

**`lowLink`**: The smallest discovery index reachable from the node's DFS subtree, including itself. This is the key insight of Tarjan's: if `lowLink[v] === index[v]`, then `v` is the root of an SCC — all nodes currently on the stack above `v` form a strongly connected component with `v`.

### `strongConnect(nodeId)` — Step by Step

```ts
const strongConnect = (nodeId: string): void => {
    // 1. Assign discovery index and lowLink (initially same)
    indices.set(nodeId, index);
    lowLinks.set(nodeId, index);
    index++;

    // 2. Push onto the DFS stack
    stack.push(nodeId);
    onStack.add(nodeId);

    // 3. Iterate over outgoing edges (filtered by projection)
    for (const edgeId of outgoingEdges) {
        const edge = graph.edges.get(edgeId);
        
        // Skip edges not matching the projection's relationship kind
        if (edge.relationshipKind !== projection.relationshipKind) continue;
        
        // Skip target nodes not matching the projection's node kind
        if (targetNode.kind !== projection.nodeKind) continue;

        if (!indices.has(targetNodeId)) {
            // 3a. Target not yet visited — recurse
            strongConnect(targetNodeId);
            // After recursion, update lowLink with child's lowLink
            lowLinks.set(nodeId, Math.min(lowLinks.get(nodeId)!, lowLinks.get(targetNodeId)!));
        } else if (onStack.has(targetNodeId)) {
            // 3b. Target already on stack — back edge found (cycle!)
            // Update lowLink with target's index (not lowLink — this is intentional)
            lowLinks.set(nodeId, Math.min(lowLinks.get(nodeId)!, indices.get(targetNodeId)!));
        }
        // If target is visited but NOT on stack, it belongs to a completed SCC — ignore
    }

    // 4. Check if this node is an SCC root
    if (lowLinks.get(nodeId) === indices.get(nodeId)) {
        // Pop everything above this node off the stack — they form an SCC
        const component: string[] = [];
        while (true) {
            const componentNodeId = stack.pop()!;
            onStack.delete(componentNodeId);
            component.push(componentNodeId);
            if (componentNodeId === nodeId) break;
        }
        stronglyConnectedComponents.push(component);
    }
};
```

### Why Use `indices.get(targetNodeId)` Instead of `lowLinks.get(targetNodeId)` for Back Edges?

This is a subtle but critical point in Tarjan's implementation. When we find a back edge to a node already on the stack:
- We use `indices.get(targetNodeId)` (discovery time), NOT `lowLinks.get(targetNodeId)`.
- This is because `lowLinks` may not be finalized yet (the target is still on the stack, its own DFS is ongoing in the call chain above us).
- Using the stable `index` value guarantees correctness.

### Self-Loop Detection

Tarjan's naturally produces SCCs of size 1 for every node that is visited but has no cycle. The `isCyclic` helper filters these trivial SCCs:

```ts
private isCyclic(component: string[], relationshipKind: RelationshipKind): boolean {
    if (component.length > 1) return true;  // Multi-node SCC is always cyclic

    // Single-node: only cyclic if it has a self-loop
    const nodeId = component[0];
    const edgeIds = this.graph.outgoingEdges.get(nodeId) ?? [];

    return [...edgeIds].some((edgeId) => {
        const edge = this.graph.edges.get(edgeId);
        return (
            edge !== undefined &&
            edge.relationshipKind === relationshipKind &&
            edge.targetId === nodeId   // ← Self-loop check
        );
    });
}
```

### Full Execution

```ts
for (const nodeId of nodeIds) {          // Iterate all nodes of the projected kind
    if (!indices.has(nodeId)) {          // Only start DFS from unvisited nodes
        strongConnect(nodeId);
    }
}

return stronglyConnectedComponents
    .filter((component) => this.isCyclic(component, projection.relationshipKind))
    .map((component) => ({ type, nodeIds: component }));
```

The outer loop ensures every disconnected component of the graph is visited. `strongConnect` is called only on nodes not yet discovered, so no node is processed twice.

## Time and Space Complexity

| Resource | Complexity |
|----------|-----------|
| Time | O(V + E) per cycle type, where V = nodes of that kind, E = edges of that relationship kind |
| Space | O(V) for the stack, indices map, and lowLinks map |

Running all 5 cycle types costs O(5 × (V+E)) in the worst case, which is still O(V+E) with a constant factor.

## What the Result Tells You

Each `Cycle` object in the result tells you:
1. **`type`** — what kind of dependency is cyclic (`file-import`, `symbol-call`, etc.)
2. **`nodeIds`** — the set of nodes forming the cycle

> ⚠️ **Important**: The `nodeIds` array contains the members of the **Strongly Connected Component**, not an ordered cycle path. For a 3-node cycle A→B→C→A, all three IDs will be present, but they may be in any order. The SCC formulation is more useful than a single cycle path because one SCC may contain many interleaved individual cycles.

## Design Notes

**Why five separate projections?** Each projection asks a different semantic question about a different layer of the codebase:

- `file-import` cycles → module system problem (circular requires/imports)
- `symbol-call` cycles → algorithmic problem (mutual/direct recursion)
- `symbol-inheritance` cycles → type system violation (A extends B extends A is illegal in TypeScript)
- `symbol-implementation` cycles → unusual but representable in the graph
- `symbol-instantiation` cycles → factory/constructor patterns that mutually instantiate each other

Keeping them separate lets the caller fix each category independently.

**Recursive `strongConnect` vs. iterative DFS**: The current implementation uses recursion. For very deep call graphs, JavaScript's call stack could be exhausted. A future hardening step is to convert `strongConnect` to an iterative DFS using an explicit stack, which would remove the stack overflow risk.
